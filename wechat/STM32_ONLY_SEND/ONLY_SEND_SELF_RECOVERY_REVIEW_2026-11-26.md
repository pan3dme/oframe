## 1. 当前判断

**当前程序已经有较好的 MCU 死机恢复基础，但 GPS、射频和供电异常的恢复还没有形成完整闭环。适合继续实测，尚不能据此承诺无人值守户外设备遇到异常都能自行恢复。**

你反馈“基本正常运行两天没死机”，这是实机稳定性的有效进展。不过，它还没有回答：GPS 不吐数据时是否恢复、LoRa 只完成本地发送却收不到回包时是否恢复、模块必须断电才恢复时怎么办，以及低电压下会不会反复启动耗尽电池。

本次检查的是目录里的当前源码。`main.c` 最近修改时间为 11 月 26 日；没有读取设备 Flash 或连续现场日志，因此不能确认“两天运行”的设备镜像与当前源码完全相同。

按影响分类：

| 能力 | 当前判断 | 依据或边界 |
|---|---|---|
| 主程序死循环、tick 停止、常见异常中断 | 已有恢复机制 | IWDG、阶段期限、Fault 处理；仍依赖供电和看门狗时钟有效 |
| STOP 无法按时醒来、RTC 停走 | 已有多层保护 | 三 RTC 秒分段、清醒 RTC 监控、看门狗复位、LSI 兜底 |
| LoRa 从深睡恢复 | 路径设计合理 | 每次正式准备发送时硬复位并完整初始化，不只是唤醒 MCU |
| LoRa SPI 卡住、TX/RX IRQ 丢失 | 能触发恢复，方式偏重 | 多数直接重启 MCU，部分故障可绕过退避 |
| LoRa 参数写错、芯片能 SPI 通信但业务失效 | 检查不足 | 大部分寄存器仍盲写；TX_DONE 不等于远端收到了 |
| LoRa 需要真正断电才能恢复 | 当前软件接口覆盖不到 | 只有 RST 控制，未发现独立射频电源控制 |
| GPS 无数据、无有效语句 | 有任务超时，缺少模块恢复 | 搜到超时后结束；没有 UART→RESET_N→断电的分级处理 |
| GPS 异常硬复位 | 尚未实现 | PA3 仅初始化为高，未发现业务复位脉冲 |
| 弱电池、反复掉电后的保命与恢复 | 部分覆盖 | 30% 限制 GPS、Flash 事务、故障退避；未形成欠压迟滞和故障能耗闭环 |

## 2. 已有的保护，后续应保留

### 2.1 MCU 看门狗不是简单“随便喂”

`Core/Src/reliability.c:26` 在 HAL、系统时钟和普通外设初始化前启动 IWDG。`Safety_Feed()`（92 行）同时检查阶段期限；HAL tick 不再推进时不能无限重复刷新看门狗。NMI、HardFault、MemManage、BusFault、UsageFault 均进入记录原因后复位的路径（`Core/Src/stm32f1xx_it.c:69` 起）。

当前 IWDG 参数是 `/256`、重装载值 `1561`。按 STM32F103 数据手册的 LSI 30～60 kHz 范围推算，超时约为 **6.66～13.33 秒**，40 kHz 典型值约 10 秒。它不是精确的十秒定时器。[S1]

### 2.2 长休眠分段、确认时间推进后才喂狗

`enterStopUntil()`（`Core/Src/main.c:1711`）将长等待分为最多三个 RTC 秒的段。每段进入前刷新一次 IWDG，伪唤醒不会直接允许再次喂狗，必须等 RTC 达到该段目标。停止 SysTick、恢复 tick 和屏蔽/恢复 LoRa、GPS IRQ 的流程已经存在。

另外，`Safety_CheckRtc()`（`reliability.c:105`）独立于阶段反复设置，清醒时约 3 秒看不到 RTC 变化就复位。RTC 相关故障会留下 LSI 提示，重启后可以绕过 LSE。

这可以覆盖不少“CPU 没死，但调度时钟不走”的情况。ST 文档也确认 IWDG 可在 STOP 中继续运行。[S1][S2]

### 2.3 LoRa 每轮深睡后会完整硬复位

`loraTryInit()`（`main.c:614`）临时禁止 EXTI2，拉低 PA1 20 ms、释放后等 100 ms，再做 `rf_init()`、默认参数和配置功率设置，最多三次。初始化后清理挂起中断。

这是实质上的射频芯片复位，已经比只恢复 MCU 时钟可靠。PAN3029 厂家说明，深睡后寄存器和状态丢失，退出需要完整初始化及配置射频参数；当前主路径符合这一原则。[S3]

`loraTx()`（665 行）有约 5 秒等待完成保护；`openRxWindow4000()`（2688 行）有约 5 秒 IRQ 等待保护。SPI 等待则使用与 tick 无关的循环上限，避免在高优先级 ISR 中依赖 SysTick 超时（`Radio/src/pan3029_port.c:36`）。

### 2.4 休眠前检查和故障退避已有基础

深睡准备的部分可读寄存器有三次回读重试，整套准备最多再尝试一次；失败向上层报告。外层总线事务保存并恢复原中断屏蔽状态，避免分页 SPI 被射频 ISR 打断。

连续故障达到三次后，有 30/60/120/240 秒、再到最高 600 秒退避（`reliability.c:166`）。退避前会尝试让射频深睡，普通失败则保持复位脚低。GPS 在 GPIO 初始化时默认断电。

### 2.5 配置存储有事务保护

`Core/Src/nvstore.c` 使用日志页、CRC、提交标记和恢复过程，不是直接擦掉旧值再裸写新值；相同值不重复写。链接区域截至 `0x0800DFFF`，配置和日志使用后面的 8 KB。

这有助于处理配置写入期间掉电，但不等于已经完成实板的低电压、切电和 Flash 寿命验证。

## 3. 优先级最高的缺口

这里 P1 表示部署前应优先处理的恢复缺口或确定性业务问题；P2 表示应安排验证、完善的项目。它们不代表这些故障已经在你的设备上发生。

### P1-1：GPS 有复位引脚定义，但没有异常复位流程

证据：`Core/Inc/main.h:86` 定义 PA3 为 GPS RESET；`main.c:3305` 起只配置为推挽输出并置高。搜索整个有效业务源码，没有发现将 `GPS_RST_Pin` 拉低的执行流程。头文件也注明“触发逻辑待接好线后再加”。

`gpsPowerOn()`（3552 行）只清软件缓存、拉高 PB1、拉低 PB15，并等待一秒。它没有证明 GPS 已输出有效 NMEA，也没有在本轮 GPS 不响应时尝试 RESET_N。

**后果：**如果模块异常但 MCU、RTC 都正常，MCU 看门狗不会因为“GPS 没工作”而自动复位。当前任务会到超时才退出；以后是否恢复，取决于下一轮电源通断是否真的让模块恢复。

建议建立独立的 GPS 恢复顺序：

1. 上电并等待启动，确认接收是否正常武装。
2. 在限定时间内仍没有有效语句，先终止/清理并重启 USART 接收。
3. 仍无有效语句，再对 GPS 做一次合规 RESET_N 复位。
4. 仍失败，进行有足够掉电时间的模块电源重启。
5. 达到本轮次数/时长预算后，断电退出并上报原因，下一轮受限重试。

“有正常 NMEA、但没有定位”应按信号条件差处理，不能与“模块无输出”采用相同的频繁复位策略。

移远手册要求 RESET_N 拉低至少 100 ms 后释放，推荐 OC 驱动。若通过三极管控制，MCU GPIO 的有效极性须按实际电路确定；不能直接照搬“PA3 拉低”假定。[S5]

### P1-2：无数据的 GPS 能持续占满搜星预算，同时正常喂狗

证据：`gpsWaitForFix()`（`main.c:2229`）只检查是否拿到新鲜定位、是否达到总超时，并持续执行 `wdg_feed()`。没有“最近一次字节”“最近一次校验正确语句”的独立期限，也没有任务内 UART/模块恢复。

本次从实际函数体转换的 JavaScript 探针，在 GPS 始终无输出/无定位的模拟下，分别运行了 60、240、600 秒：每种情况均持续喂狗并一直等满预算，最后返回失败；没有触发模块恢复。此结论是软件决策复现，未在 MCU 上运行。

连续定位更需要注意：`gpsRunContinuous()`（1066 行）在一直拿不到定位时，会把指定时长保底延长到 60 分钟。GPS 和 MCU 在这段时间保持活动；任务期间没有重新采样电池，30% 门槛只基于启动前缓存。这是当前明确的业务策略，不能把它当成看门狗漏喂故障。

**后果：**一个无数据模块也可能连续消耗较长时间电量；起始电量刚过门槛、低温或电池内阻较高时尤其需要实测。

建议在保持业务计时语义的前提下增加“数据健康”检测和有限重试。是否增加任务中的临界欠压退出，应单独确认产品策略，不宜未经确认改变现有连续定位行为。

### P1-3：LoRa 的硬复位覆盖不到“必须断电才恢复”的故障

证据：有效射频接口提供 PA1 RST、PB0 CS、SPI 和 PA2 IRQ，没有发现由 MCU 控制的独立 LoRa 电源开关。项目保存的 `review-lora.png` 中，射频 VCC 也直接接在 3.3 V 网上；这张旧图不能证明现板完全相同，但支持先核实供电拓扑。

当前能执行的是：射频复位、重写参数、MCU 复位。**这些都不等价于切断模块供电。**

如果故障需要模块电源真正降下去，软件反复重启 MCU 也可能没有效果。GPS 的 PB15 开关不能用于推定 LoRa 也可断电。

建议先实测“PA1 复位是否能救回已知 RF 异常”。如果产品要求覆盖这类剩余故障，应评估独立 LoRa 电源开关；最后一级可评估独立监督器控制整机复位或断电重启。它们是待设计能力，本次没有确认现板已具备。

### P1-4：持续 SPI 故障可能绕过已有省电退避

证据：`pan3029_port.c:43` 起的 SPI 错误直接 `Safety_Reset(RESET_SPI)`，不会返回普通 `RF_FAIL`。

而启动退避流程（`main.c:3040`）在真正进入 `enterStopUntil()` 前，又会调用 `loraTryInit()`。如果该调用内部再次发生同类 SPI 故障，会直接复位，走不到后面的“保持射频复位脚低并退避”。

本次探针也确认：在 `rf_init()` 内模拟底层 SPI 复位，`loraTryInit()` 第一次尝试就被终止，没有执行三次普通失败重试。

要区分两类故障：MISO 读到 0/FF、芯片检测普通失败，可以走返回值和退避；MCU SPI 的 TXE/RXNE/BSY/MODF/OVR 异常，可能直接重新启动。不是所有“LoRa 不工作”都会绕过退避。

**后果：**特定持续故障会变成高频重启，故障次数虽有增加，却没有真正降低等待期耗电。时钟/RTC 初始化本身持续失败时也可能在进入退避前重启。

建议让故障恢复入口能依据历史原因先压住问题外设，再休眠退避；SPI 的局部恢复须有上限，仍保留 IWDG 最后兜底。启动早期应尽早把模块控制脚置为安全状态。

### P1-5：射频初始化“成功”尚未证明关键配置真的写入

证据：`rf_init()`（`Radio/src/pan3029_rf.c:534`）有 0x04 检测及多模式写读测试，这是有效的总线检测。之后绝大多数配置调用的成功判断，最终依赖 `rf_write_reg()` 等函数返回值。

但 `SPI_WRITE_CHECK` 当前未见有效定义，相关 `#if` 回读代码不启用；`rf_write_reg()`（122 行）发送完成就返回 OK。本次模拟“SPI 传输完成、芯片没接受写入”的探针，得到 OK，回读次数为零。

**后果：**初始化早期检测通过后，如果某个参数写入受到干扰丢失，后续仍可能报告成功。模块可能处于错误频点、SF/BW/CRC/模式或错误的天线/PA 控制状态。这个问题不会必然导致 MCU 死机。

建议在初始化结束做一组有针对性的可读关键参数核对；TX/RX 切换时验证必要状态；失败时有界重试并升级恢复。只应对厂家确认可可靠回读的寄存器验证，不能全局盲目打开回读，特别是自清零、状态和深睡相关寄存器。

### P1-6：部分正常信息帧会被 36 字节截断，且没有发送 NUL

证据：`main.c:665` 的 `loraTx()` 把 `len` 限制为 35，再直接从原始 `msg` 发送 `len+1` 字节。原始字符串没有在第 35 字节补终止符，因此原文超过 35 字节时，第 36 个发出的字节仍然是正文，不是注释承诺的 NUL。

例如由现有 INFO 格式可生成：

```text
原文：8|v3-23|INFO|60T|433HZ|20dbm|V2.8|999|
正文 38 字节，加 NUL 应为 39 字节。
实际：8|v3-23|INFO|60T|433HZ|20dbm|V2.8|99
只发 36 字节，无 NUL，计数和尾部分隔符被截掉。
```

已通过实际 `loraTx()` 函数体探针复现。COORD 完整坐标回包也存在可达的超长情况。这不能单独解释 MCU 死机，但会制造“设备有发送日志、云端帧却不完整”的现象，影响远程诊断和恢复确认。远端是否因缺 NUL 出问题，要另审接收端，不能据此断言远端越界。

建议按协议压缩或拆分完整字段，检查 `snprintf()` 返回长度并拒绝不完整帧；不要靠截断拼好的协议文本来满足空中长度限制。

### P1-7：MCU 重启后，在无有效下行的情况下不会自动启动 GPS 取时

证据：`timeSynced`、同步锚点均为 RAM 变量；`rtc_init()`（1655 行）每次启动实际复位备份域并清零 RTC 计数。函数头“保留计数”的注释已不符合实现。

`isInGpsWorkWindowAt()`（1387 行）在 `timeSynced==0` 时返回 0，因此正常自动 GPS 预搜不会启动。虽然有 `gpsTrySyncFromSat()` 兜底授时，它需要先有 GPS 定位；GPS 又需要自动窗口或收到 upgps 指令才会开启。

**后果：**故障复位后，设备会继续按未同步逻辑上报和收包；但如果一直没有有效下行，它不能靠现有自动路径自行启动 GPS 授时并恢复真实 GPS 时间窗。这是授时恢复缺口，不是主循环永远停止。

建议在电量允许时增加受限的“未同步过久→一次 GPS 取时”流程，或评估可靠保留 RTC/同步基准；不能让反复故障重启变成无限冷启动搜星。

## 4. LoRa 链路恢复还需要确认什么

`linkSilenceCheck()`（`main.c:1474`）用单调 RTC 累计工作时间：第一段 2 小时无有效协议交互，只标记射频需要重新初始化；再连续 2 小时才 MCU 复位。工作时间之外不累计，连续定位期间暂停，因此实际墙上时间可能超过四小时。

这里有三个边界：

1. 平时每次深睡结束本来就硬复位、初始化射频。对于已经走深睡的常见路径，“第一次静默恢复”没有增加更强的恢复动作，也没有独立断电。
2. TX_DONE 只证明芯片产生了发送完成事件，没有证明天线真正辐射正常或集中器收到该帧；收到某种有效下行也不等价于对应上报成功。
3. 集中器掉电、遮挡、设备离开覆盖区与本机 RF 故障，都可能表现为无下行。不能靠无下行就无限加大发射、频繁复位。

建议保留两种独立判据：本地射频状态健康，以及远端有效交互。以后若增加 ACK，应明确关联本次或近期上报及接收窗口，不把任意旧帧当成成功。链路失联时做有上限的模块恢复，恢复无效则进入低耗重试节奏，同时继续允许正常时隙探测。

现有“收到有效交互清除连续故障计数”也较粗：GPS、ADC 等其它故障历史不应仅因 LoRa 收到一条消息就被全部视为恢复。可逐步拆分模块故障计数，并在对应业务稳定完成后清除。

## 5. GPS 数据可靠性问题

### 5.1 尚未校验 NMEA checksum

`parseNmeaLine()`（`main.c:2015`）没有验证 `*HH`；GGA 只要质量字段 `atoi()>0` 且经纬度字符串非空，就会标记定位有效。方向、分钟范围和最终坐标范围没有在这里形成完整校验。

RMC 日期/时间也缺少完整数字、时分秒及实际月天数检查；GPS 授时未要求 GGA 和 RMC 属于同一新鲜时刻。串口毛刺可能被当成坐标或授时依据，而不是触发数据异常诊断。

建议先校验语句类型、结构、checksum、数值范围和时效，再允许刷新定位/授时健康。保持“上一条合法数据的时间”与“收到任意字节”分开。

### 5.2 UART 错误恢复已有实现，但没有结果确认

`HAL_UART_ErrorCallback()`（3537 行）重启 `HAL_UART_Receive_IT()`；项目所用 HAL 本身也会在相应错误路径处理接收状态，所以不能把它描述成完全没有串口恢复。

实际缺口是：初始化、接收完成回调、错误回调中的重新武装均未检查返回值，前台也不检查接收是否持续失活；环形缓冲满时静默丢字节，`gpsRxCount` 只统计成功入缓冲的字节。

建议记录错误类型、溢出数、重武装失败数，前台发现数据健康期限过期后重新构建接收状态。不要在 ISR 里执行长时间 GPS 复位或断电等待。

### 5.3 预搜缓存不代表发送瞬间的位置

自动预搜成功后马上关闭 GPS，在时隙到来时使用 `gpsPreFixOk` 和保存坐标发送（`main.c:1001`、2903 行）。该路径有意绕开 `gpsFixFresh()` 的 60 秒判断，预搜完成得早时会等待较长时间。

这是为准点上报和省电作出的取舍。移动设备需要明确坐标实际采样时间，避免将数分钟前的位置解释为“当前实时位置”；可增加采样年龄或调整预搜策略。本次未改变该策略。

## 6. 休眠、唤醒和电源方面的剩余风险

### 6.1 主路径顺序基本正确，但“复位/断电成功”缺少硬件证据

自动 GPS 路径是：MCU 恢复系统时钟和 UART→采电量→LoRa 保持深睡/复位→GPS 预搜→GPS 关闭→必要时再 STOP→恢复系统时钟→LoRa 硬复位和配置→到点发送。

三个 RTC 秒的小段唤醒不重复开启 GPS 和射频，这一点应保留。GPS 也不必每个小段唤醒都硬复位；只在实际开始任务或异常恢复时处理，避免冷启动和额外耗电。

但 PB15 置高不能单凭软件注释认定“GPS 完全零电流”。需检查主电源、备份电源、UART、WAKEUP、RESET_N 的真实连接及反向供电。PA3 当前长期推挽高，若直接接到可断电模块的 RESET_N，应尤其核对断电期间引脚电压和电流。

旧图 `gps8.png` 的连接器和 `review-mcu.png` 没有清楚体现当前 PA3 到 GPS RESET_N 的连接；旧图 PA3 显示未连接。因此当前能证明的是“源码预留”，不能证明现板已经接好。

移远手册对异常低压后的电源重启给出了实际电压要求：VCC 降到 100 mV 以下并保持至少 100 ms；同时有上/掉电时间要求。需要在模块电源脚测量，而不是只计时 MCU 的 GPIO 电平。[S5]

### 6.2 LoRa 最终深睡与低电流仍没有闭环检测

`rf_deepsleep()` 的部分准备有回读，但关闭 TCXO、内部电源及最终进入深睡并非全部可验证，第二套指令也是有意不回读。外层返回 OK 后，软件就设置 `loraInitialized=0`。

如果最后深睡没有真正落实，而 RTC 和喂狗仍正常，MCU 不会因为射频耗电偏大而自动报警。下一次正常唤醒的硬复位可能恢复它，但等待期间的高耗电没有被监测。

建议先用电流测量证明多个真实唤醒周期、发射之后、欠压干扰之后都能回到目标待机水平。需要覆盖“通信恢复”和“低功耗恢复”，两者分别验收。

### 6.3 当前射频驱动基线较老，延时和电源切换需要专项核对

本地驱动文件标注 V0.8 / 2024-04，之后有项目加固。厂家 2025-08 的 V1.0.1 更新说明中列出了休眠/唤醒时序、PA 关闭、TX 时 DCDC 等相关修正；2025-11 的 V1.0.2 也更新了参数。[S4]

本地深睡用 PAGE3/0x26=0x0F，厂家当前示例相应位置为 0x00。**这只是需要按芯片/模块版本核对的差异，不足以直接断定当前值错误，也不建议直接全量替换已经实测的驱动。**

`rf_delay_us()`（`pan3029_port.c:62`）仍是按 72 MHz 假设的空循环，当前工程已使用 ARM Compiler 6.24、`-Oz`。它没有依据 `SystemCoreClock` 标定实际时间。厂家示例明确要求若干切换等待达到至少 10/150 μs。[S3]

建议以硬件定时器或明确按实际时钟实现的周期计数做基准，并用逻辑分析仪实测；分别验证 HSE72、HSI64 和编译优化变化。单靠函数名“delay_us”不能证明满足最小时序。

### 6.4 LSI 兜底可维持运行，但不能直接当精密时钟

RTC 使用 LSI 时预分频固定为 39999。数据手册 LSI 范围为 30～60 kHz，因此理论 RTC 速率为 0.75～1.5 个“秒”/真实秒；代码注释中的约 ±5% 不能作为全温全压保证。[S1]

当前漂移样本上限是 ±300 秒/小时，超过则不采用。这能过滤明显错误授时，但可能同时拒绝实际较大的 LSI 漂移。长周期下会影响时隙、GPS 窗口和无下行计时。

若 RTC 与 IWDG 同用 LSI，二者漂移是相关的，不能把所有最坏误差当互相独立简单相加。需要同时测量实际唤醒节奏、看门狗余量和温漂。

此外，LSI 既是 IWDG 时钟又可能是 RTC 时钟，不属于两个完全独立的硬件故障来源。若产品必须覆盖 MCU 内部时钟/供电的共同故障，需另评估独立监督能力。

### 6.5 欠压“保命”能力需要补齐

当前电量映射基于固定 3.3 V ADC 参考；未看到 VREFINT 校正、PVD 事件处理或带迟滞的临界低电压状态机。LoRa 在电量 0% 时仍允许发送，这是已有产品策略。

PVD 监测 MCU 的 VDD，与电池分压测量不是一回事；独立电池欠压、电源跌落、充电恢复也需分别处理。若实际 VDD 偏离假定 3.3 V，电池百分比还会有测量误差。

建议保留“低电量尽量保通信”的目标，但区分普通低电量与已无法稳定带负载的临界欠压；采用恢复迟滞和有限重试，避免太阳能/弱电池条件下“启动→发射跌压→复位→再次发射”的循环。涉及现有电量策略变更时应单独确认。

## 8. 建议的实施顺序

| 顺序 | 工作 | 完成标准 |
|---|---|---|
| 1 | 确认 PA3、PB15、PB1 和 LoRa PA1 的现板连接；修复报文截断；更新当前 AC6 构建/测试基线 | 能明确说明运行的是哪个镜像，远程诊断帧完整 |
| 2 | GPS 数据健康、UART 恢复、RESET_N、合规断电重试 | 无数据故障有期限、有上限、有原因，不能只等满搜星时间 |
| 3 | SPI/射频分级恢复及退避入口加固 | 持续 SPI 故障也能进入省电等待，恢复后能重新通信 |
| 4 | 关键 RF 参数检查、IRQ 状态检查、休眠电流验收 | 能证明“配置对、能收发、能省电” |
| 5 | 未同步过久的受限 GPS 取时、临界欠压策略、模块健康遥测 | 复位/失联/弱电后能恢复正常调度，且不会无限耗电自救 |
| 6 | 需要时增加模块电源开关和独立监督器 | 覆盖当前 MCU/RST 无法解除的剩余故障 |

不建议为“安心”先添加每天固定重启。它既不能证明模块可恢复，也会增加冷启动、对时和恢复能耗；应先把具体故障的恢复路径补全。

## 9. 上板验收计划

测试必须能在解除故障后自动恢复，并确认再次回到正常低功耗状态。不要只看复位日志。

| 注入场景 | 需要观察的结果 |
|---|---|
| 主循环死循环、禁中断、tick 停止 | 在实际 IWDG 上界及启动恢复时间内重新运行；上报原因和故障阶段 |
| STOP 中 RTC 停走、闹钟事件失效、连续伪唤醒 | 不无限喂狗；能复位、必要时切换 LSI、恢复上报并再次入睡 |
| GPS 上电后无 TX 输出 | 有限时间内先恢复 UART，再尝试模块复位/断电；本轮失败后关机，不无限搜星 |
| GPS 正常输出但天线遮挡 | 正确区分“无定位”与“模块无数据”，遵守搜星预算 |
| GPS 串口错误、错误 checksum、半句和超长句 | 不采纳坏坐标/坏时间，统计错误并重新同步，后续合法数据可用 |
| GPS 主电源掉电不彻底 | 在 VCC 实测满足掉电重启条件；核对备份电源及 IO 反灌 |
| 屏蔽 LoRa TX/RX IRQ | 超时触发受限恢复，解除屏蔽后恢复收发 |
| 可控 SPI 异常、写配置丢失、模块无响应 | 对应分级恢复有效；连续失败仍能退避，不形成快速重启循环 |
| 集中器关闭数小时再开启 | 节点不无节制耗电；集中器恢复后能重新交互和对时 |
| RF 深睡最后指令受干扰 | 验证深睡电流；恢复动作能解除高电流状态 |
| 弱电池、冷启动、GPS/LoRa 负载瞬间跌压及充电恢复 | 不陷入持续重启；电源恢复后无需人工开关机 |
| HSE/LSE 启动失败和全温测试 | 时钟降级后串口、射频时序、RTC/看门狗余量均满足要求 |
| 配置保存/恢复过程中断电 | 加载完整旧值或新值；能继续保存并运行，不损坏程序区 |

建议先做不少于 3000 次真实外设电源/休眠转换的加速测试，保持模块最小稳定时间；再进行 7～14 天正常节奏连续运行和温度/供电变化测试。次数是工程验收建议，不是可靠性保证。测试时脱离会冻结看门狗或改变 STOP 行为的调试环境。

建议保留的现场遥测：启动次数/原因/阶段、各模块恢复计数、连续失联时长、最后有效 NMEA 时间、UART 错误和缓冲溢出、RF 参数检查失败、GPS/RF 最近恢复结果、电池电压、时钟来源。用紧凑可完整发送的帧编码；避免每次喂狗或每个三秒段写 Flash。
