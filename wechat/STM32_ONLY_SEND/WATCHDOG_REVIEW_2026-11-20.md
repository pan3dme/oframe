# 定位器半年户外运行：现有逻辑与看门狗审查

审查日期：2026-11-20。此轮按“先详细了解”执行，只新增审查记录，没有修改固件、通信协议或共享驱动。

## 1. 工程范围与现有流程

- MCU：STM32F103C8，Keil ARMCC5 工程；主业务在 `Core/Src/main.c`。
- LoRa：PAN3029，经 SPI1、PA2/EXTI2 中断通信。真正参与编译的驱动位于工程外 `../Common/RadioF103/src/`，不是本目录内的副本。后续修改它会影响使用该目录的其他工程。
- GPS：USART3/PB11，9600；中断向 512 字节环形缓冲写入，前台解析 NMEA。PB15 控制电源，PB1 控制 WAKE_UP；PA3 RESET_N 目前只初始化，没有异常恢复脉冲。
- 启动加载设备名、配置、功率、搜星上限、中心坐标和设备台数。首次立即准备上报；配置周期大于一分钟时，前三轮使用一分钟快速周期。
- 默认配置 `1,0M,3t,6`；上报周期允许 1～60 分钟，按设备序号/设备台数划分时隙。工作/GPS 时间窗通过两字符编码解析。
- 普通轮发类型 2 时间/电量帧，之后开三秒单次接收窗口，处理对时和下发指令，回发待处理消息。
- 自动 GPS 轮尽量提前搜星，缓存结果，在上报点发类型 1 帧，再开接收窗口。搜星失败也会上报无定位结果。
- `upgps` 使用类型 5，可单次或连续定位；连续定位没有拿到坐标时，期限可延长至 60 分钟。类型 5 上报后不开接收窗口。
- GPS 默认搜星上限四分钟，允许下发 1～10 分钟；连续上报间隔为搜星上限与三分钟中的较大值。
- 时间以 RTC 计数为底层基准，LoRa 对时为主要来源，GPS 可在未对时时兜底授时；另有晶振漂移估算和补偿。
- 空闲时 LoRa deep sleep，MCU STOP；RTC 优先 LSE，初始化失败退 LSI；当前用 WFE/EXTI17 事件唤醒，每段最多五个 RTC 秒。
- 每轮唤醒检查电量，低于 30% 跳过 LoRa 并重新安排下一轮；恢复后重新对时。

## 2. 已有保护

- `wdg_init()` 直接配置 IWDG，分频 256，重载 0x619；按 LSI 30～60 kHz 计算，超时约 6.665～13.329 秒，典型约十秒。
- STOP 中 IWDG 继续计数，所以使用五秒分段休眠，并在分段结束后喂狗。
- TX_DONE/RX_DONE 等待有五秒软件超时，触发后延时三秒再软件复位。
- LoRa 每次初始化前拉 RST；初始化失败最多三次尝试，之后复位。
- 工作时间内，两小时没有接收到 LoRa 数据会软件复位；未对时及连续定位期间跳过该检查。
- HardFault 直接软件复位；GPS UART 错误回调尝试重新开启接收。
- 启动会上报 POR/SW/IWDG 原因；IWDG/SW 重启后复位备份域，重新选择 RTC 时钟。

## 3. 优先修复的问题

### A. 连续定位正常等待时缺少喂狗（明确缺陷）

位置：`Core/Src/main.c:1239`，`gpsRunContinuous()`。

该循环只有 `gpsTask()` 和 `HAL_Delay(100)`，没有喂狗，且执行期间不会返回主循环。

例如默认四分钟间隔，某轮约十秒定位成功并完成上报，如果还有足够时间继续下一轮，会在本轮剩余的数分钟内等待；IWDG 将在等待期间到期。不能依赖外层主循环的喂狗来覆盖这个循环。

处理方向：给正常等待分支补齐受任务期限约束的服务点，同时验证连续任务总期限；不要靠无限制拉长 IWDG 超时掩盖遗漏。

### B. 首次上电初始化阶段存在无看门狗保护的窗口（明确缺口）

位置：`Core/Src/main.c:3190` 至 `3208`，以及 `Error_Handler():3815` 附近。

IWDG 在 HAL、系统时钟、GPIO、SPI、两个 UART、NVIC 和 ADC 初始化后才启动。若首次上电采用软件启动看门狗的选项字节配置，HSE/PLL 或前置外设初始化失败进入 `Error_Handler()`，会打印、延时、关中断并永久等待，此时没有已经启动的 IWDG 兜底。

处理方向：先在复位后的 HSI 环境启动 IWDG，再初始化高风险时钟/外设；早期故障处理应能直接复位，不依赖调试串口和 SysTick。需读取实际选项字节确认启动模式。

### C. 循环持续喂狗与软件超时共用 HAL tick（明确结构风险）

位置：`main.c:795`、`1716`、`2862`。

TX/RX 和 RCC 等待循环用 `HAL_GetTick()` 决定退出，同时每圈无条件写 IWDG。若 tick 不再推进、相关完成标志也不变，而 CPU 仍执行该循环，就会持续喂狗，既不触发软件超时，也不触发硬件复位。

这与“卡在高优先级中断里”的情况不同：后者没有继续执行前台喂狗，IWDG 通常仍能兜底。

处理方向：喂狗必须受任务进度/明确期限约束；tick 不推进时不持续喂狗。STOP 阶段单独按可靠 RTC 进度服务，避免把暂停的 tick 当成故障。

### D. 睡眠入口没有重置看门狗预算（明确缺口，误复位条件需测量）

位置：`main.c:1859` 至 `1896`。

当前只在一段休眠完成后喂狗，进入第一段前没有保证喂狗。前面已经消耗的时间，需要与首段休眠、RTC 设置/同步耗时一起算入最短约 6.665 秒的窗口。不能只比较“五秒小于十秒”。

处理方向：验证 RTC/闹钟状态，清理唤醒标志，在真正入睡前保证本段预算；测量最差延迟，并为最快 LSI、LSE/LSI 两种 RTC 来源分别计算余量。IWDG 和 RTC 同用 LSI 时，两者时间误差相关，不能当成两个独立时钟简单叠加极值。

### E. RTC 等待超时后继续使用数据/写寄存器（明确缺陷）

位置：`main.c:1721`、`1734`、`1785`、`1800`。

RTOFF、RSF 和已有时钟源等待函数都没有返回成功/失败；计数 guard 耗尽后仍继续读写 RTC。若备份域已经选了失效的 LSE，`rtc_ensure_clock_running()` 等待后也没有明确降级。

IWDG/SW 重启时清备份域能处理部分情况，但 POR/外部复位分类和备份供电情况仍可能留下失效的既有 RTC 配置。

处理方向：等待函数返回状态；失败进入有限次恢复、重建 RTC 或停止喂狗的路径。IWDG 的 SR 同步等待超时也应有明确失败处理。

### F. RTC 高低半字读取缺少一致性校验（明确缺陷）

位置：`main.c:1744` 至 `1750`。

当前只有一次 CNTH 与一次 CNTL 读取。两次读取之间若低半字发生进位，可能拼出不一致值，影响上报时间、链路沉默判断和闹钟目标。低半字每 65536 个 RTC 秒进位一次，约 18.2 小时；这不是每次进位必现，而是存在很窄的竞态窗口。

ST 官方 F1 HAL 的 `RTC_ReadTimeCounter()` 使用高、低、高读取，并在两次高位不一致时重读低位。应采用相同的一致性思路，不能依赖现有“读高位锁存低位”的注释。

### G. STOP 标志清理与实际低功耗状态需要专门验证（代码缺口，板级结果未验证）

位置：`main.c:1845`、`1884` 至 `1896`。

EXTI17 的 PR 只在 RTC 初始化时清一次；分段唤醒后清的是 RTC ALRF/SECF，未在此路径清 EXTI17 PR。RTC Alarm NVIC 未启用，不能依赖 `RTC_Alarm_IRQHandler()` 自动清它。入睡前也没有显式屏蔽 SysTick。

ST 手册要求进入 STOP 前清相关 EXTI/外设/RTC 挂起标志。必须示波器或电流仪确认后续各段真正进入 STOP，而不只是前台在反复调用 STOP 函数。

本工程明确记录 ALRIE/WFE 的批次实测行为；后续应保留可用唤醒方式，先核对实际芯片与波形，不直接套用另一种唤醒方案。

## 4. 半年运行还必须覆盖的恢复与持久化问题

### 链路沉默检查不能代表完整业务健康

位置：`main.c:1613`、`2480`、`1329`。

- 未对时时 `isInWorkWindow()` 为零，沉默检查不会触发；因此从开机就一直没有有效对时的设备缺少这层恢复。
- 任意接收数据，包括解析无效帧都会刷新时间；这证明收到过数据，不能证明收到本系统的有效回复或成功对时。
- 非工作时间只是跳过检查，没有暂停累计；例如夜间不收包，次日工作窗口开始时可能立刻判超时。
- 真正无覆盖/中继掉电时，反复整机重启通常不能改变外部条件；当前没有故障次数限制或恢复退避。
- 应分别记录物理收包、有效协议交互、有效对时和本机任务完成情况，用单调时间累计；恢复宜分级为射频重置、可用时的模块断电、整机复位和退避。

### MCU 软件复位不能直接等同模块断电

目前射频恢复主要靠 PA1 RST；GPS 有 PB15 电源控制，但 PA3 复位没有使用。没有看到 LoRa 独立电源开关控制。

应上板验证 MCU 复位后 LoRa/GPS 是否在合理时间内恢复；如果某种故障必须切断模块供电才能恢复，软件复位本身不能保证解决。是否可实现断电恢复取决于原理图和实际接线。

### Flash 写入中途掉电会留下“魔术字正确、内容不完整”的记录

位置：`main.c:424`、`472` 及其他保存函数。

当前先擦页、先写 MAGIC，再写数据，且没有检查各次 HAL 擦写返回值。掉电或复位发生在中途，下一次启动可能把不完整内容当有效配置。

建议使用完整性校验、版本/序号、最后提交标志，并保留上一份有效记录；相同配置不重复擦写。修改存储布局时必须兼容现有设备数据。

链接区目前允许程序使用完整 64 KB，但最早的配置页从 0x0800E400 开始，应在链接配置里保留 0xE400～0xFFFF。现有历史构建大小没有达到该区域；这里是缺少增长约束，不是已证实发生覆盖。

### ADC 和分压电路是现有耗电检查项

位置：`main.c:3624`、`3656`。

ADC 初始化设置 ADON，采样后没有看到关闭；ST 手册说明 ADC 在 STOP 中也可能继续耗电，应在采样完关闭并验证下一次采样启动时序。

代码注释标明电池经 100K+100K 持续分压；若实际接线如此，4 V 时电流约 20 µA，按 180 天估算约 86.4 mAh。它是否影响半年续航取决于电池容量、供电和整体耗电，不能只由看门狗判断。

### 长期计时乘法的有效范围不一致

位置：`main.c:1928` 至 `1930`。

`localDelta < 1000000` 时使用有符号 32 位 `localDelta * 3600`，但该乘法从 596524 秒起就超出 int32 范围，约 6.9 天。常规持续对时会避免达到该条件，但无有效对时、仍有其他包刷新链路计时等路径不能保证。应改为安全中间类型，并覆盖长时间失联和回绕。

### 射频底层的额外风险

- `../Common/RadioF103/src/pan3029_port.c:26` 的 SPI 调用忽略 HAL 返回值，失败时返回零，可能把总线错误当成合法寄存器值。
- 射频 IRQ 在高优先级中断中执行 SPI 操作；SPI 的 tick 超时在低优先级 SysTick 无法执行时不可靠。IWDG 启动后可兜底此类阻塞，但会变成整机复位，而不是局部恢复。
- `pan3029_rf.c:21`、`:26` 的 ISR/前台共享收发标志没有 volatile 或明确同步声明；当前无跨模块优化时不一定复现，但应消除该隐患。
- 这些文件属于共享目录，实际修改前需要检查所有引用工程，避免影响其他固件。

## 5. 建议的加固顺序

1. 修复连续定位漏喂；提前启动 IWDG；建立不依赖日志/tick 的故障退出路径。
2. 收敛喂狗入口，给启动、射频初始化、TX/RX、搜星、连续定位及睡眠定义明确的完成条件和最大耗时。喂狗表达“当前阶段仍正常推进”。
3. 修复 RTC 读一致性、等待失败处理、分段入睡预算和标志清理；保留已验证的业务时序。
4. 将链路恢复改成有限次、分级、带退避；区分未对时、非工作时段、无覆盖和模块故障。
5. 记录更具体的重启原因、故障阶段和连续失败计数，复用现有类型 8 上报能力；不要每次喂狗或唤醒都写 Flash。
6. 增加断电安全配置存储，保留链接配置页，处理长期时间运算边界，实测休眠电流。

## 6. 上板验收重点

| 场景 | 应观察的结果 |
| --- | --- |
| 连续定位提前成功，剩余多轮 | 完整运行到既定期限，无误复位 |
| GPS 始终无数据/始终无定位 | 有限搜星、可上报失败、最终关电/回到正常调度 |
| LoRa 不产生 TX/RX 完成 IRQ | 在期限内恢复，连续失败后退避 |
| tick 停止但前台循环仍运行 | 不再永久喂狗，IWDG 能复位 |
| 前台死循环、关中断死循环、HardFault | 在规定时间内重启并恢复上报 |
| LSE 初始化失败、运行中停止、RTC 同步失败 | 有明确降级/复位路径，不永久卡在 RTC |
| 在 RTC 低半字进位附近反复读取 | 不出现跨 65536 秒的假跳变 |
| 各种剩余 IWDG 预算下进入 STOP | 不误复位，后续分段真实进入 STOP |
| 夜间无接收，次日进入工作窗 | 符合明确的工作时长累计策略 |
| 中继离线数天、收到无效帧但无有效对时 | 保持有界功耗和恢复频率，无时间溢出 |
| 在配置擦写各阶段切电/触发复位 | 启动后得到旧/新有效配置，或明确安全默认值 |
| 低电量反复跨阈值、充电恢复 | 不形成快速重启/初始化循环，可恢复对时上报 |
| 高低温、电源跌落、射频发射瞬间 | 记录复位和恢复时间，测真实电量开销 |

需要先确认的硬件事实：实际 MCU 型号/批次及选项字节，是否装 LSE，GPS 供电开关是否接通，LoRa 能否独立断电，电池容量与是否有充电来源。
